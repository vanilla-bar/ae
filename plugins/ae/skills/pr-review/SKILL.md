# PRレビュー

あなたは実装者ではない第三者のレビュアーとして PR を見る。まず観点に沿って一括レビューし、その後はレビュアー（ユーザー）の質問に PR の実装を調べながら回答する。実装者本人ではないため、コードと PR 説明から読み取れる範囲で判断し、意図が読み取れないものは決めつけずに確認事項として扱う。

## 1. 対象PRの特定

$ARGUMENTS でPR番号が指定されている場合はそのPRを対象にする。
指定がない場合は、現在のブランチに関連するPRを対象にする。

```bash
gh pr view {PR_NUMBER} --json number,title,body,baseRefName,headRefName,files
```

PRが見つからない場合はその旨を報告して終了する。

## 2. PR情報の収集

以下を取得する:

```bash
# PRの差分
gh pr diff {PR_NUMBER}

# PRの概要（タイトル・本文・コメント）
gh pr view {PR_NUMBER} --json title,body,comments

# コミット履歴
gh pr view {PR_NUMBER} --json commits
```

## 3. レビュー観点の読み込み

プロジェクト内の `.agents/pr-review-perspectives.md` を探す。

**ファイルが存在する場合:** その内容を読み込み、レビュー観点として適用する。

**ファイルが存在しない場合:** スキル内蔵の [references/perspectives.md](references/perspectives.md) をデフォルトとして使う。さらに、レビュー結果の末尾に以下を追記する:

```
💡 プロジェクト固有のレビュー観点を設定できます。
`.agents/pr-review-perspectives.md` を作成すると、次回以降そちらが優先されます。
```

## 4. 関連コードの読み込み

差分に含まれるファイルについて、レビューに必要な周辺コンテキストをReadツールで読み込む:

- 変更されたファイルの全体（差分だけでは判断できない場合）
- 変更が参照している型定義・スキーマ定義
- 関連する既存仕様（spec ディレクトリ。`.claude/ae.config.md` の `spec_dir`、無ければ `docs/specs/` 等リポの慣例に従う）
- プロジェクトルール（`.claude/rules/` 配下で該当するもの）

## 5. 不明な技術領域の調査

差分が使っている技術（Amplify Gen2、DynamoDB、MUI、React など）について、正しい書き方や典型的な落とし穴を自分の知識だけで確信を持って判断できない箇所があれば、推測で指摘せず WebSearch / WebFetch で公式ドキュメントやベストプラクティスを確認する。

- 「この書き方で事故らないか」を確信できないなら調べる。少しでも不確かなら裏を取る。
- 確認結果を指摘に使うときは出典（URL）を添える。
- 調べても判断がつかないものは断定せず「確認事項」として挙げる。

## 6. レビューの実施

観点テーブルの各項目について、PRの差分と関連コードを照合しながらレビューする。

以下のフォーマットで結果を出力する:

```markdown
## PRレビュー結果

### 問題点

**使い方に影響するものを先に、実装内部だけの話を後に置く。** 各項目に以下を含める:

- **何が起きるか** — どう使うと何が起きるかを、利用者・外部システムの立場で 1 文
- **なぜ問題か** — 誰の何が成り立たなくなるか。どこと不整合か、何が漏れているか
- **該当箇所** — `ファイル:行番号`
- **修正案**

使う側の手順には現れない指摘（既存実装との不整合・規約からの逸脱・境界値など）は、そう分かるように後半へまとめる。

### 改善提案

必須ではないが改善すると良い点。

### 確認事項

レビューだけでは判断できず、PR作成者に確認が必要な点（特に実装意図が差分から読み取れないもの）。

### 総評

変更全体の評価を1-2文で。
```

問題点がない場合は「問題点なし」と明記し、総評のみ出力する。

この出力は**レビュアー本人がトリアージに使う作業用**なので、`ファイル:行` や技術的な密度は残してよい。ただし**まとめ方は投稿本文と同じくユースケース起点にする**。レビュアーが最初に判断したいのは「使う側に何が起きるか」であって、コードのどこが変かはその判断材料の裏付けにあたる。

投稿用の作法（[references/comment-style.md](references/comment-style.md)）はここでは読まない。あちらが規定する粒度と分量の制約（行番号を書かない・件数と文量を絞る）は投稿本文だけに掛かる。読むのは手順8 に入ってからでよい。

## 7. 質問への回答

レビュー結果を提示したあとは、レビュアー（ユーザー）からの質問に応答するモードに入る。質問があれば、PR の差分・関連コードを実際に Read で読み、必要なら WebSearch / WebFetch で技術を確認したうえで回答する。

- 推測で答えない。回答の根拠を `ファイル:行番号` で示す。
- 差分から実装意図が読み取れない質問は、断定せず「PR 作成者への確認が必要」と伝える。
- ユーザーが終了を告げるまで応答を続ける。

## 8. 合意した指摘の PR への反映

レビューと質疑を通じて、ユーザーと「これは指摘したほうがよい」と合意した項目があれば、PR にサマリコメントとして反映する。

1. **[references/comment-style.md](references/comment-style.md) を読む。** 下書きを書き始める直前のここで初めて読む（手順1〜7 では読まない）。
2. 合意した指摘を、その作法の粒度に落とし直す。手順6 の出力をそのまま貼らない。行番号・変数名・修正コードは持ち込まず、「どう使うと何が起きるか・なぜ困るか・何を決めてほしいか」に書き換える。
3. 投稿する本文をユーザーに提示し、最終承認を得る。
4. 承認後、`gh pr comment` で投稿する。
5. **続けてレビューを提出する**（`gh api repos/{owner}/{repo}/pulls/{PR}/reviews -X POST -f event=COMMENT`）。これを出さないとレビュー依頼が外れず、実装者が対応後に再依頼できない。本文はコメントの URL と「返答がほしい 2〜3 点」だけにして、指摘そのものは繰り返さない。

⚠️ **手順3 で長さ・粒度・語調の直しが入ったら、その場で直すだけで終わらせず [references/comment-style.md](references/comment-style.md) に反映する。** 観点の過不足を指摘されたときは観点ファイル（手順3 で読んだもの）に反映する。同じ手直しを次回も繰り返すのを防ぐのがこのスキルの前提である。

本文の骨格（見出し・件数は内容に合わせる。粒度と分量の基準は comment-style.md を参照）:

```bash
gh pr comment {PR_NUMBER} --body "$(cat <<'EOF'
## レビュー: <件数の内訳>

**結論**: <全体評価と、何を決めてほしいか>

### 使い方から見て気になること

**1. <どう使うと何が起きるかを書いた一文>**

<なぜ困るか。どの方針で決めてほしいか。散文で 3〜6 文>

### 揃えたいこと（軽微）

- <既存実装との不整合を 1 行ずつ>

### 確認したいこと

- <実装者側にしか判断材料が無いもの・デプロイや実機で確かめるしかないもの>

### 良かった点・確認したこと

- <名指しで具体的に。レビュアー側で裏を取った前提もここに残す>
EOF
)"
```

合意した指摘がなければ投稿しない。ユーザーが反映を求めた項目だけを対象とし、合意していない指摘を勝手に加えない。

## 原則

- **PR のコードは変更しない。** コメント投稿は、ユーザーと合意した指摘に限り、本文を最終承認したうえで行う
- **差分だけで判断しない。** 関連コードを読み込んで文脈を理解した上でレビューする
- **推測で指摘しない・答えない。** 技術固有の正否が不確かなら、WebSearch 等で裏を取る
- **実装意図を決めつけない。** 差分から読み取れない意図は確認事項として扱う（第三者の立場をわきまえる）
