# レビューコメントの作法

**読むタイミング**: 手順8 で PR に投稿する本文を書き始める直前。手順1〜7 では読まなくてよい。

ここで規定するのは**投稿する本文**である。手順6 のレビュー結果はレビュアー本人がトリアージに使う作業用の出力なので、この作法のうち**粒度と分量の制約は掛からない**（`ファイル:行` や技術的な密度を残してよい）。ただし**まとめ方（ユースケース起点で並べる・結論を先に出す）は手順6 でも共通**である。違うのは詳しさだけで、組み立ては同じにする。

## 読み手と、その後の流れ

読み手は実装者である人間で、自分より経験の浅いメンバーであることも多い。投稿後の流れはこうなる。

> 実装者がコメントを読んで問題を理解する → 実装者が自分の言葉でコーディングエージェントに渡す → 直る

つまりこのコメントの責務は**人間に問題が伝わること**であり、機械がそのまま適用できる形にすることではない。行番号や修正パッチを書き込んでも、実装者はそこを読み飛ばして「要するに何が問題か」を探す。伝わらなければ、正確に書いてあっても価値はゼロになる。

**関係は先輩から後輩である。** 対等な相手や上位者に向けた文体にしない。過剰にへりくだると、決めてほしいことが要望なのか感想なのか読み取れなくなり、かえって相手の負担になる。「〜してください」「〜を決めてください」「〜は戻さなくていいです」と言い切る。そのうえで、良かった点は具体的に名指しで書く。断定を避けるのは**技術的な確信度が低いとき**だけで、立場を理由に濁さない。

## 粒度

**書く**

- どういう使い方をすると何が起きるか。
- それがなぜ困るか（誰の何が成り立たなくなるか）。
- どの方針で決めてほしいか。選択肢が複数あるなら並べて、決定を委ねる。

**書かない**

- 行番号。
- 変数名・関数名・型名。
- 修正コード、修正後の差分。
- ファイルパスの羅列。
- 修正案・対応方針の提案。「こうすれば直る」は書かない。**選択肢を並べる形にすると提案に化けやすい。**「A なら X する、B なら Y する、のどちらかでしょうか」は提案である。「A か B かを決めてください」で止める。
- 相手を立てるためだけの一文。「納得しています」「やり方は任せます」「〜という理解で合っていますか」は、無くても意味が通るなら削る。
- **相手側の語彙**。PR 説明や設計 doc の造語・略号（`DoD-A`、`単発ホップ`、判断番号など）をそのまま使わない。相手が AI に書かせた語彙をこちらが引き継ぐと、文章が急に借り物になる。自分の言葉に置き換える。

**「どの方針で決めてほしいか」と「どう直すか」は別物である。** 前者は書く（決定を委ねるために要る）。後者は書かない（実装者の領分であり、レビュアーが先に手を出すと選択肢を狭める）。「A のままにするか、B が成り立つ形にするか決めてほしい」までが範囲で、B の実現手段まで踏み込まない。手段を書きたくなったら「実装の細かいやり方はお任せします」で止める。

場所は「どの API か」「どの画面か」「どのドキュメントのどの節か」程度で足りる。エンドポイント名・仕様書の節番号・Issue 番号は実装者と共有された語彙なので使ってよい。判断の目安は「**実装者がこれを読んで、自分で該当箇所を特定できるか**」である。特定できるなら、それ以上細かく書くのは読みにくさにしかならない。

## 指摘の芯を構造で言い切る

症状を並べただけの指摘は弱い。「ここが漏れている」「ここも漏れている」と列挙するのではなく、**なぜ漏れが起きたのかの構造に名前を付けて、その構造ごと突く。**

よく効く型は、非対称・逆転・欠落の 3 つである。

- **非対称**: 似た 2 つが違う扱いを受けている。「厚いほうにさらに足して、薄いほうは薄いまま」
- **逆転**: 手当ての厚さと必要性が逆を向いている。「困る頻度が高いほうに手当てが無い」
- **欠落**: 決めごとが宣言されているのに実装されていない。「ADR が定義した便益が実装に無い」

構造を名指しできると、指摘の重みが変わる。件数を数えて非対称を裏付けられるならそうする（「4xx は 18 種類あるのに 5xx は 3 種類」のように、実装者が自分で確かめられる数字がよい）。そのうえで「意図した非対称なのか、片方から書き始めて片方が手つかずになったのか」を問う形にすると、責めずに再考を促せる。

## 分量

長さは正確さより優先される制約として扱う。

- 指摘は多くても 7〜8 件。重要なものから並べる。
- 重要な指摘は 3〜6 文。軽微なものは 1 件 1 行にまとめて別セクションへ落とす。
- 見出しは 3〜5 個。入れ子は 1 段まで。
- 指摘本文をテーブルで並べない。密度が上がるほど読み飛ばされる。

書き上げたら通しで読み、「これは人間が読む文章か」を自問する。長い・入れ子が深い・記号が多いと感じたら、正確さを削ってでも短くする。

## 型（構成）

1. **結論**を先頭に。全体評価と重要度（マージブロッカーか、確認・提案ベースか）を先に言い切る。続けて**「やってほしいこと」を 3 つ前後の箇条書きで出す**。読み手が最初に知りたいのは「結局この PR で自分は何をするのか」で、それが本文を読み終わるまで分からない構成は、内容が正しくても認知負荷が高い。残り（軽微な指摘・フォローアップ）は「これ以外は軽微」「これは直さなくていい」と結論の中で先に軽く扱い、期待値を確定させる。
2. **判断してほしいこと**。決定が要るものだけをここに置く。1 件に絞れるなら絞る。厚く書いてよいのはここだけ。
3. **直してほしいこと**。手を動かせば済むもの。重いものを 1 つ散文で書き、残りは 1 行ずつ落とす。
4. **確認したいこと**。判断材料が実装者側にしかないもの。**動作確認は「いつやりますか」ではなく「sandbox で動作確認はしましたか」と聞く**。マージ前に sandbox で検証するのが既定の流れなので、未着手を前提にした聞き方をしない。
5. **フォローアップの候補**。この PR の外にある同型の問題。**レビュアーが Issue を起票しない。**「こちらで Issue に起こします」と引き取ると、実装者から判断の機会を奪う。「起こすかどうかは見て判断してください」で渡す。ここで直してほしいわけではないことも明記する。
6. **良かった点**。名指しで具体的に書く。レビュアー側で裏を取った前提（ドキュメントに当たった、実機ログを読んだ等）もここに残すと、実装者が二重に確認しなくて済む。

**濃淡をつける。** 全セクションが同じ密度で並ぶと、どれが重いのか読み手に伝わらない。重い 1 件だけを散文で厚く書き、他は箇条書き 1 行に落とす。件数が多いこと自体は問題ではなく、**軽重が判別できないことが問題**である。

### 受容を問うときの形

設計上のトレードオフを受け入れた箇所に疑問があるとき、「意図した受容ですか」と聞かない。是か非かの二択になり、実装者は「はい」と答えて終わる。**「避けたリスクと、引き換えに生まれたリスクを並べて比べたうえでこちらを選んだ、と言い切れる形にしてください」**と、比較の宣言を求める。片側しか書かれていないなら、どちらが欠けているかを具体的に指す。

## 温度感

- です・ます調。
- **やってほしいことは言い切る。**「〜してください」「〜を決めてください」「〜は戻さなくていいです」「〜は触らなくて大丈夫です」。判断を濁すのは優しさではない。
- 柔らかい語尾（「〜に見えます」「〜気がします」）を使うのは、**技術的な確信度が低いところだけ**にする。全編に散らすと、確信のある指摘とそうでない指摘の区別が消える。
- 温度を下げる一言は 1 通に 1 回で足りる。「今すぐ全部直してほしいわけではありません」「ここで直してほしいわけではありません」。多用すると全体が要望に見えなくなる。
- 一人称の素の言い回しを混ぜる。「一点気になったのが」「あわせて確認したいのですが」「ぶら下がる話が 2 つ」。
- 確信が持てない技術的判断は断定せず確認事項として渡す。出典がある指摘は URL を添える。

## 投稿前にスタイルを合わせる

このリポジトリでのレビュアー自身の直近コメントを読み、語調・構成の癖を合わせる。書き出す前に一度実行する。

```bash
gh api "/repos/{owner}/{repo}/issues/comments?per_page=100&sort=created&direction=desc" \
  --jq '[.[] | select(.user.login=="{レビュアーのlogin}")] | sort_by(.created_at) | reverse | .[0:3] | .[] | .body'
```

同じ人が同じリポジトリに書き続けている文章に寄せるのが、いちばん確実にレビューコメントらしくなる。

## AI 臭さを避ける

機械が書いた感じを消す。以下を避ける。

- **em dash（—）**。読点・句点・括弧で繋ぐ。
- **記号の多用**。`→` `＝` `／` を矢印・等号がわりに連発しない。関係は文章で書く。
- **過剰な bold とテーブル**。bold は指摘の見出し程度に絞る。
- **定型句の濫用**。「〜という点」「〜が挙げられます」「〜が重要です」「総じて」「まず／次に／最後に」。
- **完全に対称な並列構造**。全項目が同じ骨格の箇条書きで埋まらないよう、散文と箇条書きを混ぜる。
- **借り物の AI 語彙**（delve・meticulous・包括的に・シームレス など）。
- 生成したまま貼らない。語尾と構造を一度崩し、自分の言葉に直してから出す。
