# /think - 批判的要件調査モード

「何を作るか」「どこに影響するか」を明確にするための対話モード。ユーザーが見落としている制約（外部サービスの制限、既存機能との衝突、設計思想との不整合など）を批判的に調査し、実装前に障壁を潰す。

<HARD-GATE>
コードの変更・コミットは一切行わない。Read Onlyで調査と対話のみ。
ただし spec / ADR の置き場（プロジェクト設定 `.claude/ae.config.md` の `spec_dir` / `adr_dir`。既定 `docs/specs/` / `docs/decisions/`）への書き込みは許可する。
</HARD-GATE>

## プロセス

```
$ARGUMENTS を受け取る
    ↓
Issue番号？ ──yes──→ gh issue view で内容取得
    │                      ↓
    │              Issue内容を「やりたいこと」として使用
    ↓ no                   ↓
テキストをそのまま使用 ←──┘
    ↓
価値の言語化（批判的問い → 価値ステートメント案）
    ↓
ユーザーが修正/承認 ←── 必須。以降のアンカー
    ↓
関連コード・仕様を調査（Spec確認を含む）
    ↓
┌→ 質問（1つずつ）
│   ↓
│  回答を受けて追加調査
│   ↓
│  アプローチ提案（選択肢がある場合）
│   ↓
│  中間まとめ（適宜）
│   ↓
│  未決事項あり？ ──yes──┐
│                        │
└────────────────────────┘
    ↓ no
解決策セルフレビュー（独立サブエージェント）
    ↓
指摘あり？ ──yes──→ 対話サイクルに戻る
    ↓ no
ユーザーが「OK」（レビュー結果を添えて最終確認）
    ↓
Spec整備フェーズ
    ↓
モード終了
```

## 0. Issue番号の解決（該当時のみ）

$ARGUMENTS が `#123` や `123` のようなIssue番号パターンの場合：

```bash
gh issue view {番号} --json title,body,labels
```

を実行し、Issueのタイトルと本文を取得する。以降の調査では **Issueのタイトルを「やりたいこと」、本文を初期の要件情報** として扱う。

初回メッセージでIssueの内容を要約して提示する：

```
📋 Issue #{番号}: {タイトル}

{本文の要約}

この内容をもとに調査を進めます。
```

## 1. 価値の言語化フェーズ

$ARGUMENTS（またはIssueから取得した内容）に対し、コード調査に入る前に「この機能の価値は何か」を批判的に問い、言語化する。Issue起動・フリーテキスト起動のどちらでも実施する。

**これは「やらない理由探し」ではない。** 批判を通り抜けた理由がそのまま機能の価値・目的として定まり、以降の対話・判断すべてのアンカーになる。ここで価値が明確になるほど、後続の考察の精度が上がる。

**3つの批判的問い:**

| 問い                                             | 目的                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| エンドユーザーが本当に求めているのはこの機能か？ | 手段と目的の分離。「○○を追加したい」の裏にあるニーズを特定する             |
| この機能で何ができるようになるか？               | アウトカムの言語化。実装物ではなく「できるようになること」を主語にする     |
| それは機能追加なしで実現できないか？             | 代替手段の検討。この時点では枠組みレベルでよい（事実確認は調査後に再確認） |

**価値ステートメントの確定（必須）:**

問いの結果を価値ステートメント案としてまとめ、ユーザーに提示する:

```
💡 価値ステートメント案:

この機能の価値は「{誰が}{何をできるようになる}こと」。
なぜなら {批判的問いを通過した理由}。
```

ユーザーの修正・承認を**必ず**得てから次に進む。承認された価値ステートメントは以降のアンカーとして固定し、対話中の仕様判断・issue分割の判断・specの「なぜ」に一貫して用いる。

## 2. 初回調査

価値ステートメント確定後、すぐに関連コード、ドキュメントを調査する。

**Spec確認（必須）:**

`spec_dir`（既定 `docs/specs/`）で関連する spec ファイルの有無を確認する。`spec_dir` が存在しないリポではこの確認をスキップし、初回メッセージにその旨を記す。

- **specが存在する場合:** specを読み、現行仕様を把握した上で調査を進める。初回メッセージで仕様の要点を提示する
- **specが存在しない場合:** 初回メッセージでその旨を記載する（「関連specはまだ作成されていません」）

**制約チェック（必須）:**

調査と並行して、やりたいことに対する制約・障壁を批判的に洗い出す。以下の観点で確認する：

| 観点               | 確認すること                                                        |
| ------------------ | ------------------------------------------------------------------- |
| 外部サービス制約   | 利用するAPI・サービスのレート制限、料金体系、機能制限、廃止予定     |
| 既存機能との衝突   | 既存の処理フロー・データ構造・UIと矛盾しないか                      |
| 設計思想との整合   | プロジェクトのアーキテクチャ方針（CLAUDE.md, rules/）と合っているか |
| データ整合性       | スキーマ変更が既存データや他機能に波及しないか                      |
| 権限・セキュリティ | 認証・認可モデルと整合するか                                        |
| スケーラビリティ   | データ量増加時に問題が起きないか（DynamoDBのパーティション設計等）  |

全観点を毎回網羅する必要はない。**やりたいことに対して該当する観点のみ**を確認する。

制約の判断根拠を自分の知識だけに頼らない。外部サービス・ライブラリ・AWSの制約が関わる場合は、**WebSearchで公式ドキュメントを積極的に確認**し、事実に基づいて判断する。少しでも不確かなら検索して裏を取る。確認結果を共有する際は出典を明記する。

**代替手段の再確認（必須）:**

調査で事実が出た時点で、価値の言語化フェーズでは枠組みレベルだった「機能追加なしで実現できないか」を根拠付きで再確認する。既存機能で実現済みでないか、より単純な手段で同じ価値を届けられないかをコードの事実で裏づけ、該当すればユーザーに伝える。

調査結果をもとに、最初の質問をユーザーに投げる。

## 3. 対話サイクル

以下を繰り返す:

**質問:**

- **1メッセージにつき1つの質問。** 複数の論点がある場合は分割する
- 選択肢がある場合はAskUserQuestionで提示する（選びやすくする）
- 目的・制約・成功基準を理解することに集中する

**調査共有:**

- 既存コードの関連箇所（ファイルパスと概要）
- 再利用できそうなコンポーネントやサービス
- スキーマの現状と変更が必要そうな箇所

**批判的レビュー（対話中に随時）:**

ユーザーの回答や方針が固まってきた段階で、以下を自問し、懸念があれば率直に伝える：

- 「この方針は価値ステートメントに沿っているか？アンカーからズレていないか？」
- 「この方針で見落としている制約はないか？」
- 「ユーザーが暗黙に前提としていることは本当に正しいか？」
- 「もっとシンプルな方法で同じ目的を達成できないか？」
- 「この issue は 1 つのユーザー価値に収まっているか？」（複数の価値を含むなら**価値で**（実装手段・レイヤーでは割らず）分割を提案する。HOW の分解は新しい issue ではなく plan として持つ。起票自体は /think では行わない）

懸念が浮かんだら、まず **WebSearchで公式ドキュメントを確認して裏を取ってから** ユーザーに伝える。自分の記憶だけで「〜のはず」と言わない。出典を添える。

批判的レビューは「やらない理由探し」ではない。実現するために障壁を先に潰すのが目的。懸念を伝えた上で、対処法も一緒に提示する。

**アプローチ提案（選択肢がある場合）:**

- 2-3のアプローチをトレードオフ付きで提示する
- 推奨案を先に出し、理由を説明する

## 4. 中間まとめ

3-4ラリーに1回、または情報が揃ったタイミングで整理する:

```
📋 ここまでの整理:

■ 価値ステートメント
- {確定した価値ステートメント}

■ やりたいこと
- {要件の要約}

■ Spec状況
- {specファイルパス}: {存在する→要点 / 存在しない}
- {今回の変更との整合}: {一致 / 仕様変更が必要 / 新規作成が必要}

■ 影響範囲
- {変更が必要なファイル・モジュール}

■ 制約・リスク
- {見つかった制約とその対処方針。なければ「特になし」}

■ 確認済みの仕様
- {決まったこと}

■ 未決事項
- {まだ決まっていないこと}
```

## 5. 解決策セルフレビュー

未決事項が解消し解決策が固まったら、**ユーザーに最終合意を求める前に**、その解決策を独立サブエージェントで検証する。レビュー結果はユーザーの合意判断の材料になる。

**目的:** 対話で積み上がった「これで良いはず」というバイアスを排除する。対話の文脈を持たない fresh eyes に反証させる。

**手順:**

1. Agent ツールでサブエージェントを起動する（コードは読み取り専用で調査可）
2. 渡すのは以下のみ。**対話の経緯は渡さない**:
   - 確定した価値ステートメント
   - 固まった解決策の要約（変更対象・アプローチ）
3. 以下を問わせる:
   - この解決策は価値ステートメントを本当に届けるか？
   - 解き方は適切か？（コードベースの実態・設計思想と整合するか）
   - もっと単純な方法で同じ価値を届けられないか？

**結果の扱い:**

- 指摘あり → 指摘内容をユーザーに提示し、対話サイクルに戻る
- 指摘なし → レビュー結果を添えてユーザーに最終確認を求める

## 6. Spec整備フェーズ

セルフレビュー結果を踏まえてユーザーが「OK」や完了の意思を示したら、specの整備に移行する。

**リポに `spec-write` skill があれば、spec の作成・更新はそのプロトコルに従う。** 無ければ以下の簡易手順で行う。`spec_dir` が存在せずユーザーも spec を望まない場合はこのフェーズを省略してよい。

### specが存在しない場合（新規作成）

`spec_template`（既定 `{spec_dir}/_template.md`。無ければ見出しだけの素朴な構成）をベースに `{spec_dir}/{機能名}.md` として新規作成する。

- spec-write プロトコルがある場合はその frontmatter 規約に従う
- 対話で明らかになった仕様を §1〜§9 に記載する
- 確定した価値ステートメントを目的・背景に相当するセクションに反映する
- 安定度は `draft` とする

### specが存在する場合（更新）

今回の変更で影響を受ける箇所を更新する。

- 変更・追加した項目の安定度を `draft` に戻す
- 既存の `stable` 項目は変更しない
- 依存関係が変わった場合は frontmatter の `depends_on` も更新する

### 設計判断の記録（該当時のみ）

対話中に大きな設計判断（2つ以上の選択肢からの選択）があった場合、
`adr_template`（既定 `{adr_dir}/_template.md`）をベースに `{adr_dir}/` にADRを作成する。

### 終了

spec整備が完了したら:

```
✅ 調査完了。

📄 Spec: {spec_dir}/{機能名}.md（新規作成 or 更新済み）
📄 Decision: {adr_dir}/{NNNN}-{title}.md（該当時のみ）

次のアクションを指示してください。
```

## 原則

- **推測で仕様を決めない。** 不明点は必ずユーザーに確認する
- **1メッセージ1質問。** 質問を詰め込まない
- **YAGNI。** 不要な機能を提案しない
- **批判的に、しかし建設的に。** 「できない理由」ではなく「実現するために先に潰すべき障壁」を見つける。懸念には必ず対処案を添える
