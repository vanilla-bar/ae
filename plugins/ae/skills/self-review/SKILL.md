# セルフレビュー

あなたは実装者自身に代わって、指定された対象をセルフレビューする。実装の意図・要件解釈・設計判断にまで踏み込み、本人が見落としがちな考慮漏れや前提の誤りを洗い出す。

## 1. レビュー対象の特定

$ARGUMENTS からレビュー対象を判定する:

- **ファイルパス指定** → そのファイルを読んでレビュー
- **`diff`** → デフォルトブランチとのコミット済み差分をレビュー
- **指定なし** → 未コミットの変更すべて（ステージ済み + ステージ前 + 未追跡ファイル）をレビュー対象とする。未コミットの変更がない場合は「変更がありません」と報告して終了する

デフォルトブランチの取得:

```bash
DEFAULT_BRANCH=$(gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name')
```

diff時のコマンド:

```bash
git diff $(git merge-base HEAD origin/${DEFAULT_BRANCH})...HEAD
```

未コミット変更の取得:

```bash
git diff HEAD            # ステージ済み + ステージ前
git ls-files --others --exclude-standard  # 未追跡ファイル一覧（内容はReadツールで読む）
```

## 2. レビュー観点の読み込み

プロジェクト内の `.agents/review-perspectives.md` を探す。

**ファイルが存在する場合:** その内容を読み込み、レビュー対象の種類に対応するセクションの観点を適用する。

**ファイルが存在しない場合:** スキル内蔵の [references/perspectives.md](references/perspectives.md) をデフォルトとして使う。さらに、レビュー結果の末尾に以下を追記する:

```
💡 プロジェクト固有のレビュー観点を設定できます。
`.agents/review-perspectives.md` を作成すると、次回以降そちらが優先されます。
```

## 3. 関連コードの読み込み

レビュー対象から推測して、関連するファイルをReadツールで読み込む:

- スキーマ定義、型定義
- 既存仕様（spec ディレクトリ。`.claude/ae.config.md` の `spec_dir`、無ければ `docs/specs/` 等リポの慣例に従う）
- プロジェクトルール（`.claude/rules/` 配下）
- 変更対象の周辺コード

## 4. 不明な技術領域の調査

レビュー対象が使っている技術（Amplify Gen2、DynamoDB、MUI、React など）について、正しい書き方や典型的な落とし穴を自分の知識だけで確信を持って判断できない箇所があれば、推測で指摘せず WebSearch / WebFetch で公式ドキュメントやベストプラクティスを確認する。少しでも不確かなら裏を取り、出典を添える。

## 5. レビューの実施

観点テーブルに基づいてレビューし、以下のフォーマットで結果を出力する:

```markdown
## レビュー結果

### 問題点

重要度順に列挙。各項目に以下を含める:

- 何が問題か
- なぜ問題か（どこと不整合か、何が漏れているか）
- どう修正すべきか（提案）

### 改善提案

必須ではないが改善すると良い点。

### 確認事項

レビューだけでは判断できず、ユーザーに確認が必要な点。
```

問題点がない場合は「問題点なし」と明記する。

## 原則

- **レビュー対象を変更しない。** Read Only
- **関連コードを十分に読む。** 対象だけでなく周辺の文脈も把握した上で判断する
- **推測で指摘しない。** 技術固有の正否が不確かなら、WebSearch 等で裏を取ってから指摘する
