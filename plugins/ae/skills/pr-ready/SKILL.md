# /pr-ready - PR をレビュー用に準備する

PR のタイトル・本文を最新の状態から生成し、レビュー補佐情報を添えてレビュー待ちにする。
**pre-impl（実装前の方針レビュー）／ post-impl（実装後のレビュー）を最初に判定し**、それぞれに応じた本文・確認項目・補佐を生成する。
pre-impl で一度 ready にした後、実装完了後にもう一度実行して内容を再生成する運用にも対応する（**複数回実行可**）。

**引数:** `/pr-ready [PR番号]`（省略時は現在のブランチのPR）

## プロジェクト設定

リポジトリ直下の `.claude/ae.config.md` があれば読み込み、以下の値を使う（無い項目は括弧内の既定値 / 動作）。書式はプラグインの README を参照。

- `spec_dir` / `adr_dir`: spec と ADR の置き場（既定 `docs/specs/` / `docs/decisions/`）
- `backend_dir`: デプロイ後の取り消しコストが高いバックエンド定義ディレクトリ（例 `amplify/`、`infra/`、`cdk/`。未設定なら手順 7.5 をスキップ）
- `union_merge`: `.gitattributes` の `merge=union` で自動解消させているファイル（未設定なら無し）
- `post_merge_check` / `spec_check`: バックマージ後・spec 変更時に走らせる検証コマンド（未設定ならスキップ）

## 手順

### 1. 対象PRの特定

$ARGUMENTS でPR番号が指定されている場合はそのPRを対象にする。
指定がない場合は、現在のブランチに関連するPRを対象にする。

```bash
gh pr view {PR_NUMBER} --json number,title,body,isDraft,baseRefName,state
```

- ドラフト・レビュー待ち（ready）の**どちらでも対象にする**。`/pr-ready` は複数回実行できる（pre-impl で ready にした後、実装完了後に再実行して内容を再生成する運用を想定）
- `isDraft` は手順 9 の「ready にするか（初回のみ）」判定に使うので保持する
- **マージ済み / クローズ済み**（`state` が `MERGED` / `CLOSED`）の場合のみ、その旨を伝えて終了する

### 2. 未コミットの変更確認

```bash
git status
```

未コミットの変更がある場合は警告し、先に `/commit` を案内する。

### 3. ベースブランチのバックマージ

```bash
git fetch origin
git merge origin/{BASE_BRANCH}
```

`union_merge` に挙げたファイル（例: ADR インデックス）への追記同士の衝突は、`.gitattributes` の `merge=union` によりローカルマージで両採用（両方の行を残す）に自動解消される。この場合は**確認を取らずに続行**するが、union は「同一の既存行を両側で編集」したケースでも両方を残してしまうため、`post_merge_check` が設定されていれば念のためマージ後に検証する：

```bash
{post_merge_check}   # 例: pnpm exec contextlint
```

- **パスした場合**: そのまま続行する
- **失敗した場合**: union が意味的な衝突を取り違えた可能性がある。報告してユーザーの指示を待つ

`union_merge` 以外のファイルでコンフリクトが発生した場合はマージが未解決のまま残る。この場合は**自動解消せず**以下を報告し、ユーザーの指示を待つ（解消後に再度 `/pr-ready` を案内する）：

- コンフリクトが発生しているファイル一覧
- 各ファイルの競合内容の概要
- 解消の方針案（ユーザーが判断できる情報）

### 4. 変更ファイルの取得と pre-impl / post-impl 判定

以降の手順（Spec整合チェック・本文生成・確認項目・バックエンド検出・レビュー補佐）はモードと変更ファイルで分岐するため、**ここで一度だけ**取得・判定し、結果を使い回す（各手順で再スキャンしない）。

```bash
git diff --name-only origin/{BASE_BRANCH}...HEAD
```

得られた変更ファイル集合からモードを判定する:

- 変更が **`spec_dir` / `adr_dir` の spec/ADR のみ**（think フェーズの産物だけで、レビュー対象の実体がまだ作られていない）→ **pre-impl**（実装前の方針レビュー）
- それ以外（`src/`・`backend_dir` の実コードはもちろん、`.claude/` の skill 改修・ドキュメント基盤等、**何かが実際に作られている**）→ **post-impl**（実装後レビュー）

pre-impl は「レビュー対象の実体がまだ無く、spec/ADR で方針だけを問う」状態を指す。成果物がアプリコード（`src/`・`backend_dir`）とは限らず、skill やドキュメントが成果物のこともあるため、`src/`・`backend_dir` の有無だけでは判定しない。

再実行で pre-impl → post-impl に変わった場合（例: spec だけだった PR に実装が乗った）も、ここで post-impl と再判定され、本文・補佐も post-impl 用に再生成される。

### 5. Spec整合チェック

手順 4 の変更ファイル集合に spec の変更（`spec_dir` 配下）が含まれるか確認する。

spec の変更がある場合、リポに `spec-write` skill があればそのプロトコルに従い、以下を確認する（skill も `spec_check` も無ければこの手順はスキップ）:

- frontmatter が spec-write の規約どおり記入されているか
- `spec_check`（例: `pnpm run lint:spec-integrity`）がパスするか

不備があればユーザーに報告し、修正してから進める。

### 6. Push

```bash
git push
```

### 7. PR内容の自動生成

コミット履歴からPRタイトルとサマリーを自動生成する：

```bash
git log origin/{BASE_BRANCH}..HEAD --oneline
```

- **タイトル**: 変更の要約（70文字以内）
- **本文**: PRテンプレートに従って生成する。既存の本文に `Closes #xxx` がある場合はそれを保持する

**テンプレートの読み込み（プロジェクト固有を優先）:**

最初に `.agents/pr-template.md` の存在を確認する:

```bash
test -f .agents/pr-template.md
```

- **存在する場合（優先）:** `.agents/pr-template.md` を **必ず先に読み**、ファイル全体を PR 本文の雛形としてそのまま使う。HTML コメント (`<!-- ... -->`) は記載ポイントなので残す（GitHub 上では非表示になる）。references/pr-template.md は読まない
- **存在しない場合のみ（フォールバック）:** スキル内蔵の [references/pr-template.md](references/pr-template.md) を読む。完了報告（手順10）で以下を追記する:

```
💡 プロジェクト固有の PR テンプレートを設定できます。
`.agents/pr-template.md` を作成すると、次回以降そちらが優先されます。
デフォルトのテンプレートをコピーして編集しますか？
```

ユーザーが希望した場合、デフォルトの内容を `.agents/pr-template.md` にコピーして編集を促す。

雛形の `<placeholder>` 部分（例: `<何をなぜ変えたか>`、`<docs/ 配下に追加・変更したドキュメントがあれば...>`）はコミット履歴と変更内容から具体的な内容で置換する。既存の本文に `Closes #xxx` や `## 完了条件` セクションがあれば、いずれも**そのまま保持する**（`## 完了条件` は `/cut` で Issue から転記された不変の受け入れ基準。ここで書き換えない）。

**確認項目は Issue 由来を優先、テンプレはフォールバック:**

- `## 完了条件` がある場合（Issue 由来）: 確認はこの完了条件が兼ねるため、テンプレの「## 確認したこと」セクションは**本文に含めない**
- `## 完了条件` が無い場合のみ（テキスト起票の PR 等）: フォールバックとしてテンプレの「## 確認したこと」セクションを本文に含める

### 7.5 バックエンド変更の検出と専用セクション生成

`backend_dir`（例: `amplify/`）配下はデプロイ後の取り消しコストが高い（DB スキーマ・認可・ストレージ・Lambda・IaC 等）。`backend_dir` が未設定ならこの手順はスキップする。
変更がある場合は、レビュアーが見落とさないよう専用セクションを本文に追加する。

手順 4 の変更ファイル集合に `backend_dir` 配下が含まれるかを見る（pre-impl では定義上含まれないので、このセクションは挿入されない）。含まれなければセクションごと挿入しない。

ヒットしたら、本文の「## 変更内容」セクションの直後に「## バックエンドの変更」セクションを挿入する。
セクション本文は `git diff origin/{BASE_BRANCH}...HEAD -- {backend_dir}` の出力を読み、
変更内容を **やや詳しめ** に箇条書きで生成する:

- データモデル変更なら、どのモデルに / どのフィールドを追加・削除・型変更・必須化したか、
  GSI の追加削除キー変更を明記
- 認可ルール変更なら、どのモデルの認可をどう変えたか（緩める方向 / 厳しくする方向 / テナント境界の影響）
- ストレージ・関数・CDK 構成等も同様に変更点を具体的に書く

セクション生成の目的は「デプロイ後の取り消しコストが高い変更を、レビュアーが見落とさないようにする」。
網羅性より **破壊的になり得る変更** を優先して書く。

### 8. PR本文プレビューの表示とチェック項目の選択

確認項目の選択（8.2）は **post-impl のみ**。pre-impl は検証できる実装がまだ無いため、チェック項目の選択は行わず、`## 完了条件` は未チェックのままにして 8.1 のプレビュー表示だけ行う。

#### 8.1 本文プレビューを通常テキストで表示する

AskUserQuestion の preview に押し込まず、独立したアシスタント発話として以下を表示する:

```
## PR内容プレビュー

**タイトル:** {TITLE}
**ブランチ:** {CURRENT_BRANCH} → {BASE_BRANCH}

**本文:**

\`\`\`markdown
{BODY（「確認したこと」セクションは仮で全て未チェック）}
\`\`\`
```

#### 8.2 チェック項目の選択（AskUserQuestion）

確認項目は **テンプレート (Step 7 で読み込んだ `.agents/pr-template.md` または references) の「## 確認したこと」セクションのチェックリスト** から動的に抽出する。スキル側で固定リストを持たない。

確認項目は **Issue 由来の完了条件を優先**し、テンプレの「## 確認したこと」項目は **Issue 由来が無いときだけのフォールバック**とする。両方を同時に並べない。

1. PR 本文に `## 完了条件` セクションのチェックボックスがある場合（Issue 由来）:
   - それ（の文言）を確認項目とする。**テンプレの「## 確認したこと」項目は使わない**
2. `## 完了条件` が無い場合のみ（テキスト起票の PR 等、Issue 由来が無い）:
   - フォールバックとして、テンプレ本文の「## 確認したこと」セクション直下の `- [ ] xxx` 行を抽出して確認項目とする
3. 上記いずれかの確認項目を、`- [ ] ` を除いたテキスト部分にして AskUserQuestion の選択肢にする
4. 加えて「該当なし」も選択肢に含める（最小オプション数 2 を満たすため、および「すべて未チェック」を表現するため）
5. multiSelect: true で複数選択可

回答後の処理:

- Issue 由来（手順 1）の場合: 選択されたら `## 完了条件` セクションのチェックボックスを `- [x]`、未選択なら `- [ ]` のまま。セクションは複製・移動せず、その場で更新する
- フォールバック（手順 2）の場合: 選択を `- [x] xxx`、未選択を `- [ ] xxx` として「## 確認したこと」セクションに展開する
- 「該当なし」が選ばれた場合はすべて `- [ ]` のまま

抽出した項目が 4 個（「該当なし」を含めて）を超える場合は、テンプレを見直して項目を絞ることを推奨する。

### 9. PRを更新してレビュー待ちに変更

```bash
gh pr edit {PR_NUMBER} --title "{TITLE}" --body "$(cat <<'EOF'
{BODY}
EOF
)"
```

**現在ドラフトの場合のみ** レビュー待ちにする（手順 1 の `isDraft` が true のとき）。再実行で既に ready の場合はスキップする:

```bash
gh pr ready {PR_NUMBER}
```

### 9.5 レビュー補佐コメントの投稿

他の開発者の PR をレビューする際、レビュアーが spec→how のリンクを追えるよう補佐情報を PR コメントに投稿する（自分の PR でも投稿してよい。読み飛ばせる）。

#### 9.5.1 モードの参照

判定は**手順 4 で済んでいる**ため再スキャンしない。手順 4 のモード（pre-impl / post-impl）に従って次の補佐内容を生成する。

#### 9.5.2 補佐内容の生成

**post-impl の場合（実装の how にフォーカス）:**

diff の機械的な列挙ではなく、「**どうやって作ったか**」をレビュアーが把握できるよう、実装方針・設計判断を記述する。実態を掴むため差分は読むが、出力は how に絞る。

```bash
git diff origin/{BASE_BRANCH}...HEAD -- src/ {backend_dir}   # 実態把握用（出力にそのまま貼らない）
```

次のような「どうやって？」に答える（該当するものだけ）:

- **責務の切り分け**: 一つの処理を、どこまでバックエンド（`backend_dir`）／どこからフロントエンド（`src/`）に分けたか。その境界をなぜそこに引いたか
- **技術・ライブラリ選定**: 何を使って実装したか（したか）。代替案があれば、なぜそれを選んだか
- **データ／処理の流れ**: 主要な機能がどのコンポーネント・関数を通って実現されているか
- **spec/ADR との対応**: リンクが追いにくい箇所のみ、どの spec/ADR をどこで実装したか

網羅性より、**レビュアーが見落としやすい箇所・破壊的になり得る箇所**を優先する。

**pre-impl の場合（実装方針）:**

コードがまだ無いので、これから**どう作るか**の方針をレビューに掛ける。

- `.claude/plans/` にこのブランチ/Issue に対応するローカル plan ファイルがあれば、その内容を方針として要約・転記する（**ファイルは gitignore のまま。内容だけ**をコメントに出す）
- plan が無ければ、コミット済みの spec/ADR から実装方針サマリを生成する

#### 9.5.3 投稿

本文を一時ファイルに書き出し、先頭に非表示マーカー `<!-- claude-review-aid -->` を付けて投稿する:

```bash
gh pr comment {PR_NUMBER} --body-file {一時ファイル}
```

投稿後、一時ファイルは削除する。コメント冒頭に pre-impl / post-impl のどちらとして生成したかを 1 行記す。

### 10. 完了報告

PRのURLを表示する。pre-impl / post-impl のどちらでレビュー補佐を投稿したかも添える。
